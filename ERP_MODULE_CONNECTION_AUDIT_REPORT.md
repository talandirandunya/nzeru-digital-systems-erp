# ERP Main Module Connection Audit

**Audit date:** 2026-09-20  
**Application:** ERP MAIN Django ERP  
**Audit type:** Read-only integration, routing, authorization, workflow, and data-connection review

## 1. Executive Summary

The ERP modules are broadly connected through the shared `accounts.User`, `Company`, governance, notifications, audit, and dashboard infrastructure. The core business workflows are not isolated, and all major application namespaces load successfully.

The system is not fully uniform. The most important remaining concerns are:

1. Meetings action-item notifications can fail because company ownership is not resolved through the parent meeting.
2. Marketplace public product access does not consistently enforce marketplace visibility.
3. Several cross-company relationships rely on form or view validation instead of model/database enforcement.
4. Procurement and account migrations are out of sync with the current model code.
5. Finance has no complete payment approval workflow despite having approval-related capabilities.
6. The configured static directory does not exist.

## 3. Shared Architecture

### Authentication and tenancy

- Custom user model: `accounts.User`
- Company ownership is represented through `User.company` and company foreign keys on business models.
- Login and company context are handled through middleware.
- Most views scope queries using `request.user.company`.

### Authorization

The system uses two complementary controls:

- Role-based access through `role_required`.
- Capability-based access through `capability_required` and `has_capability`.

Governance capabilities include module access and approval authority, including:

- `employees.manage`
- `finance.manage`
- `hr.manage`
- `procurement.approve`
- `approvals.decide`
- `admin.manage_users`
- `admin.manage_organisation`

### Approval system

The existing governance system provides:

- `ApprovalWorkflow`
- `ApprovalStep`
- `ApprovalRequest`
- `ApprovalDecision`
- `AuditEvent`
- Capability and role matching
- Approval limits and amount ranges
- Company scoping
- Self-approval prevention
- Notifications
- Row locking for approval decisions

Connected approval workflows:

- Employee onboarding
- User account creation
- Procurement requisitions
- HR leave requests
- Main dashboard approval center

### Notifications

Notifications are generated by governance and multiple business modules. Approval-required and approval-decision notifications link to the approval queue. Notification related objects are stored through type and integer ID rather than a database foreign key.

### Audit events

`governance.AuditEvent` is append-only at the model level. It records:

- Actor
- Company
- Module
- Action
- Object type and ID
- Before and after state
- Reason
- IP address
- Timestamp

## 4. Connected Workflows

### Employee onboarding

Employee creation can submit an employee to the governance approval engine. Approval decisions update the employee status.

**Status:** FULLY CONNECTED

### User account creation

Managed user creation can create an inactive account and submit it for approval. Approval decisions activate or keep the account inactive.

**Status:** CONNECTED

### Procurement requisitions

Requisitions are submitted through governance approval. Procurement decision views use the generic approval service. Goods receiving checks the purchase order approval state.

**Status:** CONNECTED

### HR leave requests

Leave creation submits a `LeaveRequest` to the governance engine. The request remains pending if no eligible approver is currently configured. Approval updates the leave status and employee leave state.

Admins and HR-authorized users can approve other users' leave through the `hr.manage` capability. Self-approval remains blocked.

**Status:** FULLY CONNECTED

### Finance

Finance has ledger, journal, invoice, banking, reconciliation, and reporting functionality. It also defines approval-related capabilities, but no complete payment approval entity and workflow were found.

**Status:** PARTIALLY CONNECTED

## 5. Confirmed Risks and Gaps

### 5.1 Meetings notification company resolution

Meeting action-item assignment can pass an `ActionItem` directly to notification creation. The action item reaches its company through its parent meeting, but does not expose a direct `company_id`.

This can cause:

```text
ValidationError: Related notification objects must belong to a company.
```

Affected areas:

- `meetings.views.action_item_create`
- `meetings.models.ActionItem`
- `notifications.utils.create_notification`

### 5.2 Marketplace hidden-product access

Marketplace views do not consistently require `is_marketplace_visible=True` when loading stock records.

Potentially affected actions:

- Product detail
- Add to cart
- Product review creation

A client who knows a stock ID may be able to access a product that should be hidden.

### 5.3 Meetings child-object scoping

Several meeting child-object views load by primary key before applying company validation. This generally rejects unauthorized access later, but initial query scoping should be company-aware.

Affected actions include:

- Meeting note edit
- Action item edit and delete
- Action item status changes
- Attachment view, download, and delete

### 5.4 Cross-company relationship validation

The following relationships do not consistently enforce company equality at the model/database boundary:

- Inventory stock and stock category
- Purchase order lines and stock
- Goods receipt lines and purchase order lines
- Marketplace order items and stock
- Notification related objects

Some checks exist in forms, `clean()` methods, or views, but enforcement is not consistent.

### 5.5 Separate marketplace identity

Marketplace clients use a separate client/password/session system rather than the ERP user system. This is intentional but increases identity and authorization complexity.

Direct model or admin creation paths should be reviewed to ensure passwords are always hashed and session ownership is correct.

### 5.6 Migration drift

The migration audit reported model changes that do not have corresponding applied migrations.

Detected items include:

- Unapplied `accounts.0012_invitation_employee_alter_company_contact_phone_and_more`
- Procurement status changes requiring a migration similar to `procurement.0002_alter_purchaseorder_status_and_more.py`

Do not deploy without reviewing and applying the correct migrations safely.

### 5.7 Static directory warning

Django reports:

```text
staticfiles.W004: The directory management_system/static does not exist.
```

This can affect static asset collection and production deployment.

### 5.8 Documentation drift

`README.md` describes an older application structure and older model names. It does not accurately describe all current modules, deployment configuration, or the current approval architecture.

## 6. Security Review

Verified protections include:

- Company-scoped approval requests
- Cross-company approval rejection
- Role and capability matching
- Self-approval rejection
- Invalid workflow transition rejection
- Stale approval rejection
- Row locking during approval decisions
- Immutable audit event model behavior
- CSRF-protected approval actions
- Capability-gated approval endpoints

Areas requiring additional tests or hardening:

- Meetings cross-company child-object access
- Marketplace hidden stock access
- Cross-company line-item relationships
- Direct model-method bypasses for procurement decisions
- Notification related-object company resolution
- Approval routing when no eligible approver exists

## 8. Recommended Priority

### Priority 1: Fix functional/security defects

1. Resolve company lookup for meeting action-item notifications.
2. Add marketplace visibility filters to all public stock queries.
3. Scope meeting child-object queries by company at query time.
4. Add model-level or service-level validation for cross-company line-item relationships.

### Priority 2: Fix deployment integrity

1. Review and create/apply the required procurement migration.
2. Apply or verify `accounts.0012` safely.
3. Create the configured static directory or correct `STATICFILES_DIRS`.
4. Update deployment and schema checks in CI.

### Priority 3: Improve coverage and maintainability

1. Add URL smoke tests for every module.
2. Add template rendering tests for every dashboard/list/form view.
3. Add marketplace visibility and meetings tenancy regression tests.
4. Add complete finance approval workflow only after defining the payment business process.
5. Update `README.md` to match the current application.

## 9. Final Assessment

The ERP has a connected modular foundation and a functioning centralized approval architecture. The main dashboard, governance, HR, procurement, employee, inventory, CRM, projects, finance, notifications, meetings, and marketplace modules are all present in the project routing and share common infrastructure.

The system should be classified as:

**INTEGRATED BUT REQUIRING SECURITY HARDENING AND MIGRATION CLEANUP BEFORE PRODUCTION DEPLOYMENT.**

The most urgent work is not creating new modules. It is tightening tenant boundaries, fixing meetings and marketplace edge cases, and reconciling database migrations with the current model code.
